# Checking beyond the unit tests

- **Smoke test.** `npm run smoke` (`tools/smoke.mjs`) starts Vite, opens the game in headless Chrome with software GL, clears the overlay so frames run, and plays three set-ups for about 20 s each (`SMOKE_SECONDS=10` for shorter, `node tools/smoke.mjs 2` for one). It fails on a page error, a `console.error`, a feature the frame guard caught, a NaN position, a girl more than 0.6 m off the ground or a vehicle more than 2 m under it. Neither the girls nor the sound get going on their own in a run this short, so it makes them (#764): each girl is got down and asked to choose, and it fails naming one who hasn't; the audio runs live and silent (master volume 0 and Chrome's `--mute-audio`, not `muted`) with a radio on within earshot, and it fails if the audio context isn't running or the radio wasn't heard. **A test that passes only shows what ran:** so it also does what a player and the girls can do (#767, `tools/smokeActions.mjs`), each read from the game's own list, so **a new action, verb, prompt, vehicle or scene is covered with nothing added**: every `girlActions(game).all` action for each girl who can do it, every `VEHICLE_VERBS` verb on every vehicle, E on every `game.interaction.items` prompt that is available and offers an action (stood beside it, `hold` called for a held one, whatever opens closed again), a ride on every vehicle (mounted, started, throttle held 1.5 s, got off) and every `SCENES` scene. A throw in any of them fails the run naming it, and so does a list that comes back empty. What would end the run is left out, in a list at the top of `smokeActions.mjs` with why (today only the wall calendar's prompt, which calls it a day). Something that needs a state a short run doesn't reach still isn't run; add a step to `smokeActions.mjs` for it. Unit tests never build `game.js`. It needs Chrome (`CHROME_PATH` if it isn't in a usual place). It waits up to `LOAD_TIMEOUT_MS` (300 s, `tools/frameBudgetRun.mjs`, shared with the budget run) for "Ready" and prints the loading steps' times; a timeout says which of the game object, the companions and the Ready status was missing (#760).
- **What the smoke run reaches** (#767, `tools/smokeCoverage.mjs`). With `SMOKE_DEV=1` (CI sets it) the run measures with Chrome's coverage how much of `src/game.js`, of each `*Host.js` and of all of `src` it ran, with the inline source maps stripped (left in they read about 96%). It needs the dev server because the build is one bundle: there is no file to give a share to. The shares print in the log and in the job summary beside the frame budget's, and a share under its floor in `FLOORS` fails the run saying which, what it was and what to do. Each floor is 2 points under the worst of five CI runs. **To raise one:** run the Smoke job a few times (re-run it), read the shares in the summary and set the floor 2 under the lowest. **To lower one:** only when code was removed or moved, with a line in `docs/decisions/process.md`. A new `*Host.js` needs a line in `FLOORS.hosts`: `tests/smokeCoverage.test.js` fails until it has one.
- **Names asked of the game** (#767, `tests/gameNames.test.js`). A host that calls `this.g.someMethod()` throws only when that line runs, and the frame guard hides it, so a test reads the code with TypeScript's parser and fails on any property asked of the game (`this.g.x`, `this.game.x`, `const g = this.g`, a destructure of it, and a parameter called `g` or `game` in a host or in `debug/` and `console/`) that `class Game`, a `this.x =` in it or an assignment from outside never gives it. A file where `g` means something else (`vehicle/quadLoad.js`, `debug/tuneCategories.js`) is left out in the test with why. If it fails, the name was renamed, moved to a host (`this.g.farmJobs.x`) or never existed: fix the call.
- **The frame guard.** Per-frame feature updates in `game.js`'s main update go through `this.guard.run('updateX', () => this.updateX(dt))` (`src/core/featureGuard.js`), so one feature's error is logged once with its name and counted and the rest of the frame still runs. The count shows in the console's `errors` and the Tune tab's "Frame time" folder.
- **Shooting something new:** `node tools/shot.mjs --name <group.name>` or `--at <place>` (#384): four sides, a close-up of the main face (the largest side, square on, framed whole) and a contact sheet in `.scratch/shots/<name>/`, overlay cleared and checked, HUD hidden, daylight. For each shot it hides whatever is not the target and stands between the camera and any part of it (a wall, a hay bale; never the terrain or the sky), puts it back afterwards and prints what it hid, so a missing wall in a picture is explained; `--keep` leaves everything in. A thing that hangs flat on a wall shows edge-on from the side, whatever is hidden. Use it for the one look at anything new (`looks.md`) instead of copying a `.scratch/pp` script.
- **The bare-block test** (`tests/bareBlocks.test.js`, #384) builds every named set piece, barn prop, world builder, item and model class in node (`tests/helpers/worldModels.js`) and fails: a solid box of 1.5 m or more on every side anywhere in a model (also inside a merged mesh); a model of three boxes or fewer; one with under 2 meshes or fewer than 40 triangles plus 1.7 a m2 of its surface; a large one in plain colour. Existing offenders are in `KNOWN_BLOCKS`, `KNOWN_THIN` and `KNOWN_PLAIN` with a line each and never added to; the test fails when one on a list is gone. To add a new thing, call it in `buildWorldModels` with `add(kind, name, builder, call)`: the test compares what the source exports with the builders that actually ran, and lists in `NOT_MODELS` only what has no model of its own. `looks.md` has the steps.
- **Headless checks**, only for model work (one look at anything new you'll see, two rounds at most: `looks.md`) or where you can get past the "Click to play" overlay (click it every time the page loads, and confirm it in the screenshot): puppeteer-core in `.scratch/pp` (untracked) with system Chrome, existing scripts there to copy from (the "headless-browser-checks" memory). Run your own dev server from your worktree with `npx vite --port 5180` in the background; Jamie's is on 5173. Editing source while a headless check runs reloads the page under it.
- **Engine sound:** `node tools/render_engine_sound.mjs <vehicle id> out.wav` renders it offline through the real engine model and worklet (idle, full throttle, idle, half, full) in seconds. `--bank` and `--set` to compare, `--start` for the start (key, starter, catching), `--start --no-catch` for four seconds of cranking on an empty tank. Leave the WAVs in `.scratch/` for Jamie to listen to.
- **The frame budget in CI** (#364). The smoke test, while the farm is still sunny, stands you at fixed spots (spawn as the game opens, the yard, the village street, the wood's gate, the top of the pasture; each looking north, east, south and west, worst view kept), counts draw calls and triangles from `renderer.info` (the same on any machine and on every run, with the GL draws stubbed, the animals, girls, traffic and lamp halos taken out, the clock stopped, the shadow window snapped and the far detail judged from scratch: #597) and fails over `BUDGETS` in `tools/frameBudget.mjs`. The Smoke job's summary shows each spot with the change from main (the newest merge in the history below, not main measured again, #636). Locally, `node tools/budget.mjs --dist dist --out numbers.json` measures a build on its own and `--summary numbers.json` prints the table. The count is made as in a window 1000 points high (`viewHeight`), because what is too small to see is left out by the window's size (#451). A new thing that moves through the farm and could be in view (a kind of animal, a rider) goes in `MOVERS` in `measureInPage` (it is taken out of the scene for the count, not just hidden, since some things turn their own `visible` back on), or it puts the count out again, and it raises `BUDGETS.movers`, which counts everything left out as if all were in view, on purpose with a line in `docs/decisions/performance.md`. Anything the page does a little at a time after Ready (damage, wear, belts, traffic bodies) is finished first in `measureInPage`, or the count depends on how long the page has had. Raise a budget only on purpose, with a line in `docs/decisions/performance.md`. Every merge that changes what ships also adds its numbers to a history kept as a workflow artifact (the Release workflow records it after releasing, `tools/budgetHistory.mjs`, `tools/fetchBudgetHistory.sh`), and the Smoke summary shows the last ten merges for each spot (#373).
- **Time per feature.** `FeatureGuard` times each guarded feature: the console's `perf` has `slowestFeatures` and the Tune tab's "Frame time" folder lists the five slowest. It splits the "farm features" stage, so look there before profiling.
- **Frame time and loading on a real GPU:** `node tools/perf.mjs --out after.json` builds and serves the checkout itself (no dev server needed), loads it in Chrome on this Mac's GPU and reports time to "Ready" and MB fetched, then at each of the five spots the draw calls, triangles, ms a frame, worst frame and slowest features, against the frame budget and the local ones (8 ms a frame, 2.5 s to Ready, `tools/perfReport.mjs`). About 80 s for two runs. `--main` measures origin/main the same way in a throwaway worktree, `--compare before.json after.json` prints the table, `--steps` the loading steps' timeline, `--stages` where each frame's JS time goes at every spot, `--profile 10 --dev` a CPU profile by function. `--query body=flat` adds to the page's address, to measure with a flag on or off. Run it after anything that adds to the world, to every frame's work or to loading; `/perf` is built on it (`.claude/commands/perf.md`), and `perf` in the game's console gives the same figures live.
- **Stutters** (#373). `frameStats` keeps the slowest 1% of frames and counts those over 33 ms; for each long frame `core/stutters.js` names the cause (a shader prepared that frame, a drop in the heap, the stage that took the time, or the farm feature in it). The console's `perf` and the Tune tab's "Frame time" folder show them, and `perf.mjs` adds the 1% low, the long-frame count and the causes to its table. The heap is Chrome's `performance.memory` and is coarse; a long frame beside a fall of 1.5 MB or more is called a clean-up. To find what is creating objects every frame, record in Chrome's Performance panel with "Memory" ticked and look at the Allocation rate / JS heap sawtooth, then at the "Minor GC" bars under the long frames; the bottom-up view of the frames before each GC names the allocating functions.
