---
description: Work through one GitHub issue, start to finish, as a pull request that merges itself when CI passes
argument-hint: "[issue number; default: the next one]"
---

**First, `tools/upToDate.sh`.** These instructions are read from the main checkout, so if it is behind `origin/main` they are old ones. If the script doesn't print `ok`, stop and pass its message on to Jamie before choosing or starting anything (#721).

Work on GitHub issue $ARGUMENTS. If no number is given, take the next one, in this order (the plan is `docs/farm-plan.md`; the phases are the milestones in `.github/settings.yml`):

- **`alongside`** takes the lowest-numbered eligible issue in the **Alongside** milestone.
- **Otherwise**, the lowest-numbered open issue labelled `🔜 next`; or if none, the lowest-numbered eligible issue in the earliest open milestone (by title order: `0 · Foundations` first, `Alongside` last, so it is only reached by `/todo alongside`).
- **Eligible** means open, not labelled `❓ question`, `🤦‍♂️ wontfix`, `🧪 testing` or `💤 later`, with no open PR yet (`gh pr list --search "<n> in:body"`), and a `Depends on:` line (if it has one) that names only closed issues. An issue with no milestone is taken only by number.

```
gh issue list --state open --label "🔜 next" --json number,title --jq 'sort_by(.number) | .[0]'
tools/nextTodo.mjs            # the eligible issues in order, first five; `tools/nextTodo.mjs alongside` for that milestone
```

Other sessions work in this checkout at the same time, so every item gets its own worktree and branch. Never switch branch in the main checkout, and never commit to main.

1. **Say which issue it is.** Before anything else, say its number, title and link: "Working on #260: Every frame throws since asleep-on-the-back (https://github.com/jamiefdhurst/quad-bike-sim/issues/260)".
   Then **read it.** `gh issue view <n> --comments`, including its **Where it fits** section and the entry for its place in `docs/farm-plan.md` (an issue that puts something in the world isn't started before its phase, and a place that isn't on the plan changes the plan first, in its own PR). Then the `.claude/rules/` files for the areas it touches (CLAUDE.md lists them; they don't load on their own in a worktree), the "Where things stand" summary of each `docs/decisions/` area it touches, and only the code and the sections it touches; don't read the whole codebase. **If the issue says to use something as given** (a draft, a file, a map, a link) **and you can't reach it, stop and ask Jamie**: never redraw, rewrite or approximate it, however close you could get (#719). The body ends "Was TODO <old number>" for items moved from the README: DECISIONS and the code call it by that number.
   **The whole issue is the job.** Run `node tools/issueCheck.mjs start <n>`: it writes every line of the issue to `.scratch/issue-check-<n>.md`, and each one is answered before the PR opens (step 7). "Too big", "not covered" and "for later" aren't reasons to leave a line. Only two things are: it's blocked by something you can't fix, or Jamie has said so. If a line can't be done the way it says, or you think another way is better, stop and ask: don't do something else and say so afterwards (#736, #745).
2. **Ask if it needs it.** If the item adds anything you'll see, read `.claude/rules/looks.md` and copy the issue's **Looks like** list into your plan (write one from the real thing and add it to the issue if it has none). If anything is genuinely undecided, ask Jamie now: a short numbered list of questions, each with your recommendation, then stop and wait. If it's clear, say in two or three lines what you're going to do and carry on without waiting. Write what was settled as a comment on the issue (`gh issue comment`) as well as in DECISIONS.md.
3. **Make the worktree.** `tools/worktree.sh start <n>` prints its path. Do all the work there: absolute paths for every edit and command (the shell's directory resets to the main checkout), your own dev server from it (`npx vite --port 5180`) for any headless check, and the voice recording run from it so the banks land in its `public/audio`. `node_modules` and `.scratch` are links to the main checkout's; if the item changes `package.json`, delete the link and `npm ci`.
4. **Build it**, the look first as its own commit if there's something new to see, then the rest, following CLAUDE.md: pure logic with unit tests where possible, tunables with ranges, the girls' lines in the voice files (re-record in the background if you add any, wait for it, and commit the banks on the branch before the PR is merged; see `.claude/rules/voice-lines.md`).
5. **Check it cheaply.** `npm test` in the worktree, `npm run smoke` if the item touches `game.js` or adds something to the frame, and at most one short headless check if it only shows in the running game. Anything new you'll see gets one look (two rounds at most) against its **Looks like** list, every feature ticked off (`.claude/rules/looks.md`, "Checking the look"). A `🚀 performance` issue is measured before and after as `/perf` does (`.claude/commands/perf.md`, "Working an issue").
6. **Check it fits and finish the docs.** Anything you can use follows `.claude/rules/controls.md` (the key rule, a prompt, feedback), screens and messages follow `interface.md`, panel and console additions go where `debug-panel.md` says, and every name a player reads is in `docs/glossary.md`. Then finish the docs as CLAUDE.md says: the FAQ's answers in `src/faq/faqContent.js`, `docs/` if the item changes something a page there describes, a section at the end of the area's file in `docs/decisions/` and its summary line if the item changes how something stands (headed with the issue number, and its old TODO number if it had one: what was decided, why and any numbers measured, in about ten lines, without what wasn't checked), and ASSETS.md for any asset.
7. **Answer the issue, line by line.** Run `node tools/issueCheck.mjs start <n>` again, in case the issue changed, and go through `.scratch/issue-check-<n>.md` with the issue and your diff (`git diff origin/main...`) side by side. Read each line for everything it asks, not its gist: a list of cases means every case, and a phrase like "for its size" is part of the job. Tick a line only when you can name where it is, on the `→` under it: a file, a test in backticks or a command you ran; `context:` for a bullet with nothing to do. **A line saying something fails or refuses: see it fail**, with a throwaway change, and try one way round it. Fix what this turns up before going on. A line you can't do stays unticked with why under it. **A line you did another way isn't ticked, however good the reason:** mark it `- [~]`, with what you did instead and why under it, and ask Jamie. On a yes, start its note `Jamie agreed:` with his words. Until then it can't close the issue (#745).
8. **Commit and open the PR.** First `node tools/issueCheck.mjs post <n>`: it posts the list as a comment on the issue and prints the line the PR must use, `Closes #<n>` when every line is ticked or agreed, otherwise `Part of #<n>`. Never write "Closes" over it: the required Test check fails a PR that would close an issue with a line unanswered. With `Part of`, the issue stays open, and when the PR has merged you carry on with the rest in this session if you can. Commit in sensible chunks on the branch, with messages written for a player (they become the FAQ's "Recently changed"), staging your own files by name. Before pushing, `git fetch origin && git rebase origin/main`; if the voice banks conflict, take main's and rebuild yours with `--bank-only`. Then:
   ```
   git push -u origin HEAD
   gh pr create --title "<what changed, for a player>" --body "<the line it printed>. <what it does and why>" --label "<each of the issue's labels>"
   gh pr merge --auto --merge
   ```
   The PR carries the issue's labels: exactly one type label, which decides the release's version bump (`✨ feature` minor, anything else patch), and `💥 breaking` on top only if an old farm save won't load or loses something (major). CLAUDE.md, "Versions and releases", says which; the required "Version label" check fails without one and says what the merge will release as. No AI attribution anywhere, and no Testing or Known limitation sections in the body.
9. **Wait for the merge.** `node tools/waitMerged.mjs <pr>`, run in the background, and wait for it to finish. It polls until the PR has merged and prints `merged <time>`, or stops and says why (a failed check by name, a conflict, the PR closed, auto-merge off). Not `gh pr checks --watch`: that returns when the checks finish, or at once if none have started yet, before the merge (#727). On a failure, read the log (`gh run view <run id> --log-failed`), fix it in the worktree, commit, push and run it again (a failed `Issue check` only needs the list answered, posted and `gh run rerun <run id> --failed`); on a conflict, rebase on `origin/main`, push and run it again. Never merge it by hand past a failing check. **The item isn't finished, and you don't say it is, until this has printed `merged`.**
10. **Clean up.** Only after step 9 printed `merged`: `tools/worktree.sh finish <n>`. The issue closes from the PR's "Closes #n". A merge that changes what ships makes a release on its own (`.github/workflows/release.yml`); the merge is the end of the item, so don't wait for the release.
11. **Ask for testing if it needs it.** If something you didn't check could be wrong in a way Jamie would want fixed, and only the running game can show it (how it looks, how it feels, a line by ear, what a girl does in play), open one testing issue for the item; otherwise none. Number tweaks and things the tests cover don't need one. **A testing issue is for eyes and ears only** (a look, a feel, a line by ear, how it plays), never for what a test could assert: what a prompt says and whether it carries its key, what a toast says, that a sound is triggered, a refusal and its reason, a value a command sets. Write those as tests first (with a stand-in game where `game.js` is involved, as `tests/villageHost.test.js` does). Every console command or panel button you put in a checklist is looked up in `src/console/gameTree.js` (or tried through `game.console.shell.run` in a headless page) before you write it. At most one per item: If an open testing issue for the same area hasn't been started yet (no ticked lines), add this item's lines to it as a new section headed "Also try #<n>, merged in <PR link>" instead of opening another, so Jamie can test an area in one go (`/test <area>`).
    ```
    gh issue create --title "Try: <the issue's title>" --label "🧪 testing" --label "<each of the issue's area labels>" --body "<body>"
    ```
    The body, short: `Try #<n>, merged in <PR link> (v<version>).`, then **Get there** (the quickest way: a "Make her do" button, a console command such as `girl amy tip`, a `to <place>`), **Try** (a checklist, `- [ ]`, one thing to do and see per line), **Right looks like** (what you expect, with any number worth eyeing), and **Not checked** (what the session couldn't see). No type label: it's not a change. The "not checked" list lives here now, not in DECISIONS.md.
12. **Tell Jamie**, only after step 9 printed `merged`. The first line says whether the whole issue is done: "All 14 lines of #384 are done" or "11 of 14 lines of #384 are done, and it stays open", with a link to the comment, each undone line with why, and each line done differently with what Jamie agreed. Then, in a few lines, what changed, anything you did differently from what the issue asked and why, what you checked and what you didn't, the PR link and when it merged, the version it releases as (from the Version label check's summary) and the testing issue's link if you opened one.

One issue per session. When it's done, stop; Jamie will start a fresh session for the next one. **Ideas stay out of the PR and out of the report**, as one at the end reads like something unfinished: one worth keeping is filed (`gh issue create --label "❓ question"`, a few lines on what and why), and the report says only "Filed #<n>, a separate idea: nothing in this issue depends on it".
