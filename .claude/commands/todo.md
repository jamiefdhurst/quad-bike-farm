**First, `tools/upToDate.sh`.** These instructions are read from the main checkout, so if it is behind `origin/main` they are old ones. If the script doesn't print `ok`, stop and pass its message on to Jamie before choosing or starting anything (#721).

Work on GitHub issue $ARGUMENTS. If no number is given, take the next one, in this order (the plan is `docs/farm-plan.md`; the phases are the milestones in `.github/settings.yml`):

- **`alongside`** takes the lowest-numbered eligible issue in the earliest open **alongside** milestone, 6 to 12 (`ALONGSIDE` in `tools/nextTodo.mjs`): work that doesn't depend on where things are, done while the map's phases run.
- **Otherwise**, the lowest-numbered open issue labelled `🔜 next`; or if none, the lowest-numbered eligible issue in the earliest open milestone (by the number its title starts with: `0 · Foundations` first, the alongside milestones once 5 is done, `13 · Ready for players` last).
- **Eligible** means open, not labelled `❓ question`, `🤦‍♂️ wontfix`, `🧪 testing` or `💤 later`, with no open PR yet (`gh pr list --search "<n> in:body"`), and a `Depends on:` line (if it has one) that names only closed issues. An issue with no milestone is taken only by number.
- **`--solo`** anywhere in the arguments (`/todo 851 --solo`, `/todo alongside --solo`) turns off the second opinion in "Before you stop", at the end, and the recheck before the PR (step 8), for the whole session, to save their cost.

```
gh issue list --state open --label "🔜 next" --json number,title --jq 'sort_by(.number) | .[0]'
tools/nextTodo.mjs            # the eligible issues in order, first five; `tools/nextTodo.mjs alongside` for the alongside milestones
```

Other sessions work in this checkout at the same time, so every item gets its own worktree and branch. Never switch branch in the main checkout, and never commit to main.

1. **Say which issue it is.** Before anything else, say its number, title and link: "Working on #260: Every frame throws since asleep-on-the-back (https://github.com/jamiefdhurst/quad-bike-sim/issues/260)".
   Then **read it.** `gh issue view <n> --comments`, including its **Where it fits** section and the entry for its place in `docs/farm-plan.md` (an issue that puts something in the world isn't started before its phase, and a place that isn't on the plan changes the plan first, in its own PR). Then the `.claude/rules/` files for the areas it touches (CLAUDE.md lists them; they don't load on their own in a worktree), the "Where things stand" summary of each `docs/decisions/` area it touches, and only the code and the sections it touches; don't read the whole codebase. **If the issue says to use something as given** (a draft, a file, a map, a link) **and you can't reach it, stop and ask Jamie** (after "Before you stop"): never redraw, rewrite or approximate it, however close you could get (#719). The body ends "Was TODO <old number>" for items moved from the README: DECISIONS and the code call it by that number.
   **Check it is ready.** Run `node tools/issueLint.mjs <n>` (#774). It fails an issue that still has questions in its body, has more than 12 lines of its own work, has no **Done when** or a line in it that shows nothing, has no `Scale:` where it needs one, names a path that isn't there or a console line that doesn't run, or hands work to an issue that doesn't take it. On a failure, stop and ask Jamie before anything else (after "Before you stop"): list each problem with a proposed fix (for one too big, the split as new issues of at most 12 lines, each `Depends on:` the one before). On his yes, edit the issue with `gh issue edit`, or file the split and carry on with the first part. Don't guess at a gap or work round it.
   **The whole issue is the job.** Run `node tools/issueCheck.mjs start <n>`: it writes every line of the issue to `.scratch/issue-check-<n>.md`, and each one is answered before the PR opens (step 7). "Too big", "not covered" and "for later" aren't reasons to leave a line. Only two things are: it's blocked by something you can't fix, or Jamie has said so. If a line can't be done the way it says, or you think another way is better, stop and ask: don't do something else and say so afterwards (#736, #745).
2. **Plan every line, then ask if it needs it.** Before the worktree, give each line of `.scratch/issue-check-<n>.md` a note on one line starting `plan:`: where the change goes (a file or module) and what will prove it (a test, a command, a `scene`, or "by eye"), so a line you don't understand shows now, not at step 7 (#775). Then `node tools/issueCheck.mjs plan <n>`: it names every line without a plan and posts the list on the issue, 0 done. A line you can't plan (unclear, blocked, or needing a choice) goes into the questions to Jamie below, and you stop for them. If the item adds anything you'll see, read `.claude/rules/looks.md` and copy the issue's **Looks like** list into your plan (write one from the real thing and add it to the issue if it has none). If anything is genuinely undecided, ask Jamie now (after "Before you stop"): a short numbered list of questions, each with your recommendation, then stop and wait. If it's clear, say in two or three lines what you're going to do and carry on without waiting. Write what was settled as a comment on the issue (`gh issue comment`) as well as in DECISIONS.md.
3. **Make the worktree.** `tools/worktree.sh start <n>` prints its path. Do all the work there: absolute paths for every edit and command (the shell's directory resets to the main checkout), your own dev server from it (`npx vite --port 5180`) for any headless check, and the voice recording run from it so the banks land in its `public/audio`. `node_modules` and `.scratch` are links to the main checkout's; if the item changes `package.json`, delete the link and `npm ci`.
4. **Build it**, the look first as its own commit if there's something new to see, then the rest, following CLAUDE.md: pure logic with unit tests where possible, tunables with ranges, the girls' lines in the voice files (re-record in the background if you add any, wait for it, and commit the banks on the branch before the PR is merged; see `.claude/rules/voice-lines.md`).
5. **Check it cheaply.** `npm test` in the worktree, `npm run smoke` if the item touches `game.js` or adds something to the frame, and at most one short headless check if it only shows in the running game. Anything new you'll see gets one look (two rounds at most) against its **Looks like** list, every feature ticked off (`.claude/rules/looks.md`, "Checking the look"). A `🚀 performance` issue is measured before and after as `/perf` does (`.claude/commands/perf.md`, "Working an issue").
6. **Check it fits and finish the docs.** Anything you can use follows `.claude/rules/controls.md` (the key rule, a prompt, feedback), screens and messages follow `interface.md`, panel and console additions go where `debug-panel.md` says, and every name a player reads is in `docs/glossary.md`. Then finish the docs as CLAUDE.md says: the FAQ's answers in `src/faq/faqContent.js`, `docs/` if the item changes something a page there describes, a section at the end of the area's file in `docs/decisions/` and its summary line if the item changes how something stands (headed with the issue number, and its old TODO number if it had one: what was decided, why and any numbers measured, in about ten lines, without what wasn't checked), and ASSETS.md for any asset.
7. **Answer the issue, line by line.** Run `node tools/issueCheck.mjs start <n>` again, in case the issue changed, and go through `.scratch/issue-check-<n>.md` with the issue and your diff (`git diff origin/main...`) side by side. Read each line against its `plan:` note too: a line built other than planned says how, in its note after the plan, and one done another way is a `[~]` line as below. The plan is not evidence: put the proof on the lines after it, as `node tools/issueCheck.mjs post` reads only those. Read each line for everything it asks, not its gist: a list of cases means every case, and a phrase like "for its size" is part of the job. Tick a line only when you can name where it is, on the `→` under it: a file, a test in backticks or a command you ran; `context:` for a bullet with nothing to do. **A line saying something fails or refuses: see it fail**, with a throwaway change, and try one way round it. Fix what this turns up before going on. A line you can't do stays unticked with why under it. **A line you did another way isn't ticked, however good the reason:** mark it `- [~]`, with what you did instead and why under it, and ask Jamie (after "Before you stop", as for a line left undone because it is blocked). On a yes, start its note `Jamie agreed:` with his words, as the first line under it, above its `plan:` (the check reads the note from its first line). Until then it can't close the issue (#745).
8. **Recheck it before the PR** (#1178), unless the arguments say `--solo`. When the issue is labelled `🌾 world` or `🏍️ vehicles`, or `git diff --shortstat origin/main...` (with anything uncommitted) shows more than 150 changed lines, run `.claude/commands/recheck.md` on the worktree now, as written there, so what the reviewer finds is fixed on the branch rather than filed as a bug after the merge. Make its pack after the list is answered. An agreed `fix` is fixed and committed on the branch, with its line and evidence in the list brought up to date, before `node tools/issueCheck.mjs post`; an `ask` goes to Jamie in the same stop as step 7's `[~]` and blocked lines (after "Before you stop"), so he is asked once. Its step 5 posts the count line on the issue, once a round, naming the model this session runs on; don't post another. Neither condition met: no recheck, and no count line.
9. **Commit and open the PR.** First `node tools/issueCheck.mjs post <n>`: it posts the list as a comment on the issue and prints the line the PR must use, `Closes #<n>` when every line is ticked or agreed, otherwise `Part of #<n>`. Never write "Closes" over it: the required Test check fails a PR that would close an issue with a line unanswered. With `Part of`, the issue stays open, and when the PR has merged you carry on with the rest in this session if you can. Commit in sensible chunks on the branch, with messages written for a player (they become the FAQ's "Recently changed"), staging your own files by name. Before pushing, `git fetch origin && git rebase origin/main`; if the voice banks conflict, take main's and rebuild yours with `--bank-only`. Then:
   ```
   git push -u origin HEAD
   gh pr create --title "<what changed, for a player>" --body "<the line it printed>. <what it does and why>" --label "<each of the issue's labels>"
   gh pr merge --auto --merge
   ```
   The PR carries the issue's labels: exactly one type label, which decides the release's version bump (`✨ feature` minor, anything else patch), and `💥 breaking` on top only if an old farm save won't load or loses something (major). CLAUDE.md, "Versions and releases", says which; the required "Version label" check fails without one and says what the merge will release as. No AI attribution anywhere, and no Testing or Known limitation sections in the body.
10. **Wait for the merge.** `node tools/waitMerged.mjs <pr>`, run in the background, and wait for it to finish. It polls until the PR has merged and prints `merged <time>`, or stops and says why (a failed check by name, a conflict, the PR closed, auto-merge off). Not `gh pr checks --watch`: that returns when the checks finish, or at once if none have started yet, before the merge (#727). On a failure, read the log (`gh run view <run id> --log-failed`), fix it in the worktree, commit, push and run it again (a failed `Issue check` only needs the list answered, posted and `gh run rerun <run id> --failed`); on a conflict, rebase on `origin/main`, push and run it again. Never merge it by hand past a failing check. **The item isn't finished, and you don't say it is, until this has printed `merged`.**
11. **Clean up.** Only after step 10 printed `merged`: `tools/worktree.sh finish <n>`. The issue closes from the PR's "Closes #n". A merge that changes what ships makes a release on its own (`.github/workflows/release.yml`); the merge is the end of the item, so don't wait for the release.
12. **Ask for testing if it needs it.** If something you didn't check could be wrong in a way Jamie would want fixed, and only the running game can show it (how it looks, how it feels, a line by ear, what a girl does in play), add lines for it to the walk for its place; otherwise none. Number tweaks and things the tests cover don't need any. **A walk is for eyes and ears only** (a look, a feel, a line by ear, how it plays), never for what a test could assert: what a prompt says and whether it carries its key, what a toast says, that a sound is triggered, a refusal and its reason, a value a command sets. Write those as tests first (with a stand-in game where `game.js` is involved, as `tests/villageHost.test.js` does). Every console command or panel button you put in the lines is looked up in `src/console/gameTree.js` (or tried through `game.console.shell.run` in a headless page) before you write it. Never open a "Try: ..." issue of its own (#1179): Jamie tests by walking a place, so each place on `docs/farm-plan.md` has one open walk issue ("Walk: the farmstead"), and an item that isn't placed goes to the walk for its first area label ("Walk: the girls", "Walk: vehicles", "Walk: sound").
    ```
    node tools/walkIssue.mjs place <n>     # the walk the item's lines go to, and why; pass --place to add if it's wrong
    node tools/walkIssue.mjs add <n> --pr <PR link> --lines .scratch/walk-lines-<n>.md
    ```
    `add` finds the open walk for the place and adds a section headed "Try #<n>, merged in <PR link>", or opens the walk if there is none (a walk closes when every line is ticked, and the next item there opens a fresh one). The lines file, short: **Get there** (the quickest way: a "Make her do" button, a console command such as `girl amy tip`, a `to <place>`), **Try** (a checklist, `- [ ]`, one thing to do and see per line), **Right looks like** (what you expect, with any number worth eyeing), and **Not checked** (what the session couldn't see). The "not checked" list lives here, not in DECISIONS.md.
13. **Tell Jamie**, only after step 10 printed `merged`. The first line says whether the whole issue is done: "All 14 lines of #384 are done" or "11 of 14 lines of #384 are done, and it stays open", with a link to the comment, each undone line with why, and each line done differently with what Jamie agreed. Then, in a few lines, what changed, anything you did differently from what the issue asked and why, what you checked and what you didn't, the PR link and when it merged, the version it releases as (from the Version label check's summary) and the walk its lines went to, with its link, if you added any. Last, run `node tools/recheckRate.mjs`: if its last line starts `ask:`, end the report with the rate it gives and its question (whether to narrow the recheck to world and vehicle-model items), with its recommendation. It asks only once 20 items built on Opus have a count, and stops once `docs/decisions/process.md` records Jamie's answer under "Narrowing the recheck".

One issue per session. When it's done, stop; Jamie will start a fresh session for the next one. **Ideas stay out of the PR and out of the report**, as one at the end reads like something unfinished: one worth keeping is filed (`gh issue create --label "❓ question"`, a few lines on what and why), and the report says only "Filed #<n>, a separate idea: nothing in this issue depends on it".

## Before you stop

Every stop that puts a question or a finding to Jamie gets a second opinion first (#876): step 1's lint failure and unreachable source, step 2's questions, and step 7's `[~]` lines and lines left undone because they are blocked, with step 8's asks from the recheck. `tools/upToDate.sh` isn't one, as there is nothing to check. Skip it when the arguments say `--solo`, or when this session already runs on Opus: your system prompt names the model you run on, so look there rather than guess (#1010). Jamie asked for this subagent, so launch it without asking him.

- **Launch** it with the Agent tool: `subagent_type: "general-purpose"`, `model: "opus"`. Not a fork, which keeps this session's model.
- **Give it** the pack, from `node tools/reviewPack.mjs <n>` (it writes `.scratch/review-pack-<n>.md`: the issue and its comments, `.scratch/issue-check-<n>.md`, and the "Where things stand" summary of each area's file in `docs/decisions/`), the worktree path, the finding and the draft question word for word, and every command the question rests on, with its output.
- **Ask it to** read the pack once rather than fetching the issue again, re-run what the question rests on, check the reasoning (numbers compared like for like, from the same run and the same version of the code; the issue read in full; the area's summary), and answer each question as **settled** (with the evidence: a file, or a command and its output), **corrected** (new wording, and a recommendation) or **fine as it is**.
- **Tell it to keep it cheap** (#1010): answer only the questions put to it, not review the rest of the work; batch its reads (several commands in one Bash call, or calls side by side), as every request reads its whole context again; open no images; and stop at about 12 requests, saying what it couldn't settle rather than digging on.
- **Tell it never to** decide what is Jamie's (a look, a feel, scope, a line of the issue changed), edit or commit files, comment on GitHub, or write to the main checkout's `.scratch/`. A worktree's `.scratch` is a link to it, so a tool run there overwrites shared results (#851): it copies anything a tool would write before running it, puts it back after, and checks with `cmp`.
- **Then ask Jamie** the checked questions. Drop a settled one, saying in a line what settled it, and add one line saying what the check changed, or "Checked by a second opinion: no change".
